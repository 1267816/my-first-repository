# 第 4 章实操记录：实验 1 - 看引用链（Reference Viewer）

## 🎯 实验目的

亲眼验证“硬引用连坐机制”，体会一个资产如何通过硬引用拖家带口，导致内存膨胀。

## 🛠️ 实操步骤（我做了什么）

1. 在内容浏览器右下角开启“显示插件内容”。
2. 搜索并定位到 `ShooterCore/Experiences/B_ShooterGame_Elimination`。
3. 右键该资产，选择打开“引用查看器 (Reference Viewer)”。
4. 初始“搜索依赖性深度”为 1 时，观察直接引用的资产线条。
5. 将“搜索依赖性深度”改为 2，观察引用网络的爆炸式扩张。

## 📊 运行结果

- 深度为 1 时：中心是 Experience，周围有一圈粉红色的线（硬引用）指向其他资产。
- 深度为 2 时：屏幕瞬间被大量密集的线填满（“一大坨”），延伸出诸如 `HeroData_ShooterGame` 等节点，每个节点又引出更多线条。
- （观察：粉红色线代表硬引用，白色线代表类继承等其他关系）。

## 🧠 结论与总结

1. **现象与预期完美吻合**：硬引用的确会引发“拔萝卜带出泥”的连锁反应，深度只加了 1，复杂度就呈指数级上升。
2. **印证的架构原理**：这就是为什么第 4 章强调要把“只在特定模式用、体积大”的资产改成**软引用**。如果是硬引用，加载这个 Experience 就等于把下面一整张蜘蛛网全加载进内存。
3. **避坑指南**：在项目后期，如果发现加载卡顿、内存爆炸，一定要用 Reference Viewer 检查是不是哪里不小心写了硬引用。

## ⚠️ 当前欠下的技术债（待回补）

- 引用查看器中的“白色线”具体代表哪些 C++ 底层关系（如 UClass 继承、Outer 归属等）。
- 引擎底层是如何通过 `UObject` 序列化系统顺着这些引用链加载资产的（牵涉到 UHT 和反射）。

# 第 4 章实操记录：实验 2 - Tag 层级匹配

## 🎯 实验目的

验证 GameplayTag 的“子匹配父，父不匹配子”的层级规则，以及它如何作为系统间的契约（此处为无敌免疫机制）。

## 🛠️ 实操步骤（我做了什么）

1. 打开 `L_Expanse` 地图，以 `Play Standalone`（单机模式）运行 PIE。
2. 按 `~` 调出控制台，输入 `AddTagToSelf Cheat`，给自己加上父 Tag。
3. 输入 `DamageSelf 10`，观察血量。
4. 再次在控制台输入 `AddTagToSelf Cheat.GodMode`，给自己加上子 Tag。
5. 再次输入 `DamageSelf 10`，观察血量。

## 📊 运行结果

- 第一下 `DamageSelf 10`：**会掉血**（血量降至 90 左右）。
- 第二下 `DamageSelf 10`：**完全不会掉血**（被免疫）。

## 🧠 结论与总结

1. **现象与预期完美吻合**：只持有父 Tag（`Cheat`）时，底层代码去查子 Tag（`Cheat.GodMode`）是查不到的，所以不触发无敌；持有子 Tag 时，直接命中，伤害被拦截。
2. **印证的架构原理**：技能系统（GAS）在计算伤害时，不需要认识“作弊管理器”或“无敌系统”，它只认 `Cheat.GodMode` 这个字符串。这就是 Tag 作为“系统间解耦契约”的完美体现。
3. **避坑指南**：以后在项目里配置 Tag 拦截（比如“被眩晕时不能放技能”），拦截条件填 `Status.Stunned`，那么玩家中了 `Status.Stunned.Deep` 同样会被拦截，因为子匹配父。

## ⚠️ 当前欠下的技术债（待回补）

- `FGameplayTag` 和 `FGameplayTagContainer` 在 C++ 底层的数据结构（为什么它比字符串比较快很多）。
- `HasMatchingGameplayTag` 在底层是如何沿着 Tag 树往上遍历寻找父节点的。
